# Google Sign-In and Three-Sender Email — Setup & Reference

This document covers the two features you asked for:

1. **Google Sign-In / Sign-Up** on the login and signup pages.
2. **Three email senders** — Primary Gmail, Secondary Gmail, SendPulse (final fallback) —
   with an admin card to connect, test, and switch senders.

It also lists the **exact environment variables** each host needs.

---

## 1. Google Cloud setup (one time)

Both features use the *same* Google OAuth 2.0 Web client.

1. Open <https://console.cloud.google.com/> → create/select a project.
2. **APIs & Services → Library** → enable **Gmail API**.
3. **APIs & Services → OAuth consent screen**
   - User type: **External**.
   - Fill app name, support email, developer email.
   - **Scopes**: add `.../auth/gmail.send` and `.../auth/userinfo.email`.
   - Add yourself (and any sender accounts) under **Test users** while the app is in testing.
4. **APIs & Services → Credentials → Create credentials → OAuth client ID → Web application**.
   - **Authorised JavaScript origins** (for the frontend button):
     - `https://learnafrica-lite-weld.vercel.app`
     - your custom domain, if any
     - `http://localhost:5173` (local dev)
   - **Authorised redirect URIs** (for connecting Gmail senders):
     - `https://learnafrica-backend-hyae.onrender.com/api/admin/email/oauth/callback`
     - `http://localhost:5000/api/admin/email/oauth/callback` (local dev)
5. Copy the **Client ID** and **Client secret**.

> The Client **ID** is public (it ends up in the browser). The Client **secret**
> and all refresh tokens are stored server-side only and never sent to the frontend.

## 2. Environment variables

### Backend (Render dashboard → your service → Environment)

| Variable | Required | Purpose |
|---|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` | Yes (for both features) | Google sign-in + Gmail sender OAuth |
| `GOOGLE_OAUTH_CLIENT_SECRET` | Yes | Token exchange for sign-in and Gmail senders |
| `BACKEND_URL` | Recommended | Public backend URL so the OAuth callback returns to the right host, e.g. `https://learnafrica-backend-hyae.onrender.com` |
| `SENDPULSE_CLIENT_ID` | For SendPulse | SendPulse API ID |
| `SENDPULSE_CLIENT_SECRET` | For SendPulse | SendPulse API secret |
| `SENDPULSE_SENDER_EMAIL` | For SendPulse | A verified sender address in SendPulse |
| `SENDPULSE_SENDER_NAME` | Optional | Display name (default `LearnAfrica`) |
| `JWT_SECRET` / `SECRET_KEY` | Yes | Signing secret (auto-generated by `render.yaml`) |
| `PAYSTACK_SECRET_KEY` | Yes | Payments (app refuses to start without it in production) |

### Frontend (Vercel → your project → Settings → Environment Variables)

| Variable | Required | Purpose |
|---|---|---|
| `VITE_GOOGLE_CLIENT_ID` | Yes | The **same** Client ID. The Google button is hidden when this is missing. |
| `VITE_API_URL` | Yes | Backend URL, e.g. `https://learnafrica-backend-hyae.onrender.com` |
| `VITE_SITE_URL` | Recommended | Public frontend URL |

> After adding/updating `VITE_*` variables on Vercel you **must redeploy** — Vite
> bakes them in at build time. This is why the live site currently has no Google
> button: `VITE_GOOGLE_CLIENT_ID` is not set, so the button is (by design) hidden.

## 3. Connecting the three senders (admin UI)

Go to **Admin → Email Senders** (the `EmailSendersCard`).

### Primary and Secondary Gmail

1. Click **Connect with Google** on *Gmail account 1* → sign in with the Gmail
   account you want as the **primary** sender → grant access → close the window.
2. Repeat on *Gmail account 2* for the **secondary** sender.
3. Each row shows **Connected** and the sender address once done.

*(Alternative: **Enter a refresh token manually** if you already have one.)*

### SendPulse

Enter the Client ID, Client secret, sender email and name, then **Save SendPulse**.

### Choose the active/primary sender

Use the **Active sender** radio on any connected row. You can switch between
Gmail 1 and Gmail 2 at any time — no code change, no redeploy.

### Test each option

Paste a recipient and click **Send test** on each row. A test send targets only
that sender and never falls through to another.

### See errors

Each row shows **last_error** when a send fails. Sending status for the *whole*
system is printed on the backend logs (`email delivered via X after fallback: ...`).

## 4. Sending order and failover

Implemented in `backend/app/email_service.py` → `send_email()`:

- Order: **primary Gmail → secondary Gmail → SendPulse**.
- If the admin selected Gmail 2 as primary, the order becomes
  **gmail2 → gmail1 → SendPulse** (SendPulse is always last).
- A failing sender is retried only when the failure **cannot have delivered the
  message** (token refresh failed, not configured/connected, timeout, connection
  error, 429/quota). Failures that might mean the message was already accepted
  (e.g. `invalid recipient`, rejected) **stop** the chain — this is the
  duplicate-send guard, so the same email is never sent twice.
- A successful send clears the stored error for that sender.

## 5. Security

- OAuth **refresh tokens** and **client secrets** are stored server-side in
  `platform_settings` (`email_config`) and **never returned** by the API — the
  public config exposes only connection status, sender address, and last error.
- Sender configuration endpoints require an **admin** login.
- The Gmail OAuth state is a short-lived signed JWT bound to the slot and admin.
- Google **sign-in** verifies the ID token with Google (signature, expiry,
  audience) before trusting it; existing users keep their role; new users get
  `student`, or `instructor` (pending approval). Google can never create an admin.
